AI Lesson Generator — architecture & decisions

A K-12 teacher types a subject and grade; a two-stage AI pipeline builds a clickable deck of pedagogical moves — including a playable game — that the teacher can edit, save, and share. This is how it's built and why.

Python · FastAPI React · Vite · TS Claude · claude-haiku-4-5 structured outputs file-based store .pptx · share link

Data flow

From "generate" to a shared lesson

Generation is outline-then-fill: one call plans the moves (or the teacher fixes the sequence), then one schema-constrained call per slide runs in parallel. Media is resolved from the model's search intent — never invented. The deck lives in the browser; a teacher can save it (a file) and share it (.pptx or an HTML link).

Core idea

Everything is a block

The system is composed of two families of building blocks. Built-in blocks are typed and proven; a teacher adds custom blocks at runtime that become first-class — the planner uses them and they render — with no new code.

Slide-type blocks

A slide is a pedagogical move, not a layout. Each type owns a schema (what the AI fills) and a renderer (how it shows). sorting-game is a real, playable game — the AI supplies the data, the renderer is interactive.

hook concept check-for-understanding exit-ticket video sorting-game + custom

Custom types fill a generic CustomContent schema and render generically; unknown types are coerced to a safe default.

Pedagogy blocks

The rules that shape a lesson, factored out of the prompt into editable blocks. The lesson-planning prompt is assembled from a fixed base plus the enabled blocks — edit them and the "behind the scenes" panel shows the prompt change.

open with a hook match the grade verify understanding close with an exit ticket + custom rule

Toggle, edit, remove, or add. Enabled block texts ship with each request; the backend joins them into the system prompt.

The teacher can drive it at any level — the AI fills whatever is left blank:

LEVEL 0

Nothing

Subject + grade only. The AI is the curriculum designer.

LEVEL 1

Pedagogy

Tune the rules that shape how lessons are planned.

LEVEL 2

Block types

Define custom move types the planner can use.

LEVEL 3

Structure

Compose the exact slide sequence; AI writes each intent.

Entities

The domain model

The code is the schema — Pydantic on the backend (models.py) mirrored by TypeScript (types.ts). Slide content is validated by its type's model at fill time, then stored as a plain object for transport.

Data architecture

Where state lives

The deck and all block config live in the browser. The one piece of server-side state is the file store — no database.

Deck & blocks

React state. Edits, reorder, delete, and all block config are local — no round-trip, no persistence layer.

Saved lessons

Each is a JSON file in lessons/. Transferable and git-friendly: commit one and it appears in anyone's list after a pull.

Streaming

Generate/regenerate stream NDJSON events — the exact prompt sent and JSON returned — so the UI shows the pipeline working live.

Share & resilience

.pptx (color-coded) and a standalone HTML view link. Per-slide retry→placeholder; no key → a bundled fallback deck.

How I think

Key decisions

Every non-obvious choice is logged as chose X over Y because Z in docs/DECISIONS.md. The load-bearing ones:

D-004

A slide is a pedagogical move, not a layout

Same build cost as generic title/bullets, but defensible: the types are the teacher's actual moves. Ties the product to the K-12 user.

D-008

Outline-then-fill; the AI decides the shape

Makes per-slide regenerate and failure handling cheap, and the plan is a first-class artifact. No fixed template — unless the teacher sets one.

D-012

Everything is a block — some custom

Slide types and pedagogy are composable blocks, built-in-proven and user-extensible. A custom block enters the system with no new code.

D-010

Failure reuses the happy path

Validate → retry once → a regeneratable placeholder. A failed slide is just a slide waiting to be regenerated — same button, no error mode.

D-002

Slides are the container; video is one type

The model returns a search intent; the backend resolves a real embeddable clip (and, for other slides, a Wikimedia image).

D-011 · revisited

Started stateless; added save/share on request

Persistence was a deliberate cut for thinness. The founders asked to save and share, so I added a file store (not a DB) — still git-shareable, minimal surface.
